# Apple オンデバイス LLM と Jev の比較

同じレシート・同じ品目・同じ費目で、**速度・正解率・候補外率・料金**を測る。

## 走らせる

```sh
cd bench

# Apple（端末内）— 2つのやり方を別々に測る
swiftc -O -o apple apple.swift
./apple free   > apple-free.json
./apple guided > apple-guided.json

# Jev — API キーが要る
TYPESAFE_API_KEY='sk-...' node jev.mjs > jev-result.json

# 表にする
node report.mjs
```

キー無しで `node jev.mjs` を流すとモックになる。
モックの数字（遅延・正解・トークン）は**どれも実測ではない**ので、
`report.mjs` は Jev 行を伏せて「未実測」と出す。

## 測っているもの

| | 意味 |
| --- | --- |
| 正解率 | `dataset.json` の手付け正解と一致した割合 |
| 候補外 | **12費目のリストに無い語を返した件数** |
| 1品目 | 1品目あたりの所要時間 |
| 1レシート | レシート1枚を処理し終えるまでの時間 |
| 往復 | モデルを呼んだ回数 |

「候補外」がこの比較の肝。LT で言う「宇宙旅行費を弾くコード」が
要るか要らないか、そのものの数字になる。

## 3つのやり方

**Apple / 文字列で回答** — 候補を文章で並べて、文字列で答えてもらう。
このアプリが元々やっていたやり方。候補外の語が返りうる。

**Apple / `@Generable` で拘束** — enum で選択肢を型に縛る。
Foundation Models にも制約付き生成はあるので、公平のために測る。
ただし**成立するのは費目がコンパイル時に決まっている場合だけ**。
家計簿の費目はユーザーが編集できるので、実アプリでは enum にできない。
ここが Jev の `criteria`（実行時に組み立てる）との本当の差。

**Jev / Choice** — 費目を `criteria` に渡す。
品目数ぶんの question を並べて、レシート1枚を1往復で処理する。

## 条件を揃えたところ

- 同じ品目・同じ店の文脈を渡す
- 同じ12費目
- 1回目はウォームアップとして計測から外す
  （Apple は初回にモデル読み込みで数秒かかる。入れると比較が歪む）
- 品目ごとにセッションを作り直す
  （使い回すと前の品目が文脈に残り、並び順で結果が変わる）

**揃えなかったのは往復回数。** Jev は questions を並列評価できるので
レシート1枚＝1往復、Apple の端末内モデルは1品目ずつ。
そこが比較したい差なので、どちらも「そのやり方で一番速い形」で測っている。

## 正解データについて

`dataset.json` の `label` は手で付けた（`taxonomy.mjs` の定義に従う）。
判断が割れる品目には `ambiguous: true` と `accept` を付けてあり、
`accept` のどれかに当たれば正解として数える。

```json
{ "name": "マスク 30枚", "label": "医療費",
  "ambiguous": true, "accept": ["医療費", "日用品"],
  "why": "taxonomy では医療費>健康管理だが、日用品>衛生用品も筋が通る" }
```

**31品目はベンチマークとしては小さい。** 傾向は見えるが、
数%の差を論じられる規模ではない。LT で出すなら
「この31件ではこうだった」以上のことは言わないほうがいい。
