# 家計簿 × Jev — レシート1枚が家計簿1件になるまで

LT「Jevで作る実用アプリ：家計簿のデータ設計から動くものになるまで」のデモ。

OCR 済みのレシートテキストを、**5ステージ・API 5回**のパイプラインに通して、
家計簿に登録できる形（費目・金額・確信度つき）まで持っていく。

Jev の3つのプリミティブ（**Choice / Score / Noul**）だけで組んである。
生成はしない。全部「選ぶ・測る・判定する」。

## 動かす

依存パッケージは無い（Node の標準モジュールのみ）。`npm install` は不要。

```sh
export TYPESAFE_API_KEY='sk-...'
node server.mjs
# → http://localhost:3000
```

Node 22 で動作確認済み。

## レシート写真を読み込ませる

画面の点線の枠に **レシートの写真をドロップする**（またはファイルを選ぶ）と、
OCR してテキスト欄に入り、そのまま「Jev に通す」で分析できる。

**OCR は Jev ではできない。Jev はテキスト専用で画像を受け取らない。**
ここは Apple Vision（オンデバイス）に任せていて、`ocr.swift` がその入口。
実アプリ（iOS）も同じ Vision を使っているので、デモと本番で同じ経路になる。

初回起動時に `ocr.swift` を自動でビルドする（数秒）。手動なら:

```sh
swiftc -O -o ocr ocr.swift
./ocr receipt.png
```

macOS 専用。それ以外の環境では画像の読み込みだけが無効になり、
テキストを貼り付ける経路は普通に動く。

### 傾き補正をしている理由

レシートは「品名が左、金額が右」で1行になっているが、
Vision は品名と金額を**別々の箱**として返す。縦位置でまとめ直す必要がある。

ここで素朴に「y が近いものをまとめる」とやると、
**手持ちで撮った数度の傾きで破綻する。** 紙が3度傾くと、
横に 500px 離れた金額は 27px ほど上下にずれる。これは行の高さと同じ程度なので、
**金額が1つ隣の品名にくっつく。** しかも全部が同じだけずれるので、
画面上は一見正しく見える。かなり危ない壊れ方をする。

そこで、Vision が返す四隅から紙の傾きを推定し、座標を起こしてから行をまとめている。
-8°〜+8° の範囲で、全品目が正しい金額と対応することを確認済み。

**API キーが無いときはモックモードで起動する。**
API を呼ばずに、それらしい答えを返してパイプラインを最後まで通す。
会場の Wi-Fi が落ちたときの保険。画面に `MOCK` バッジが出るので本物と混同しない。

```sh
JEV_MOCK=1 node server.mjs   # キーがあっても強制的にモック
```

## パイプライン

| # | ステージ | 使うプリミティブ | question 数 |
| --- | --- | --- | --- |
| 1 | レシートを読む／行を仕分ける | Choice ×(行数+5) + Noul ×3 | 行数 + 8 |
| 2 | 費目を決める（大分類） | Choice ×N | 品目数 |
| 3 | 費目を決める（小分類） | Choice ×N' | 品目数（一部スキップ） |
| 4 | 品目の性質を見る | Score ×N + Noul ×2N | 品目数 ×3 |
| 5 | 家計簿として評価する | Score ×3 + Noul ×2 | 5 |

8品目のレシートで **question 64 個 / API 呼び出し 5 回**。
各ステージの往復は常に1回。Jev は questions を並列・独立に評価するので、
品目が 3 個でも 20 個でもステージの所要時間はほとんど変わらない。

## 構成

| ファイル | 役割 |
| --- | --- |
| `taxonomy.mjs` | **データ設計**。費目の階層・ルブリック・履歴。criteria の素 |
| `receipt.mjs` | 正規表現での前処理。候補を「多めに」拾うところまで（意味では判断しない） |
| `jev.mjs` | Jev クライアント。プリミティブのビルダーと確信度の式、モック |
| `pipeline.mjs` | 5ステージの本体。ここが読みどころ |
| `ocr.swift` | レシート画像 → テキスト。Apple Vision。**Jev は画像を扱えない** |
| `server.mjs` | HTTP。API キーを守るプロキシ。結果を NDJSON で流す |
| `index.html` | 画面。ステージ投影を想定して文字を大きめにしている |
| `TALK.md` | LT の構成案（8分） |

## 使っている Jev の機能

これでもかと詰め込んである。どこで何を使っているかの対応表。

| 機能 | 使っている場所 |
| --- | --- |
| **Choice**（選択肢から1つ） | **行の仕分け**・費目・業態・支払い方法・抽出（全ステージ） |
| **Score**（ルブリックで採点） | 品目の必需度、レシートの節約度・健康度・家計インパクト |
| **Noul**（はい/いいえの確率） | レシート判定・値引き・経費・衝動買い・名寄せ・予算警告 |
| 1リクエストに複数の型を混ぜる | stage 1・4・5 |
| `state` を文字列で渡す | stage 1（レシート全文） |
| `state` をオブジェクトで渡す | stage 2–5（店・品目・今月の家計を構造化して渡す） |
| `instructions` をオブジェクトで渡す | 抽出の `{field, question}`、品目の `{品目, 質問}` |
| `criteria` の値をオブジェクトで | 費目の `{what, not_for, examples}` |
| Score の段階をオブジェクトで | `{summary, signals}` |
| Noul の `criteria.true/false` | 境界が曖昧な判定（レシートか・衝動買いか・同じ商品か） |
| fan-out（N問を1リクエスト） | stage 1（行の仕分け）・2・3・4 |
| 確信度での3段階ルーティング | 全判定（自動確定 / 確認 / 手入力） |
| 階層分類（2段階 Choice） | 大分類 → 小分類 |
| 事前パース値の抽出 | 店名・合計金額・購入日（正規表現 → Choice） |
| composite scoring | 必需度を金額で重み付け（重みはコードが持つ） |
| 429 / 529 のバックオフ | `jev.mjs` の `postWithRetry` |

## 設計のポイント

### 費目は実行時に組み立てる

家計簿の費目はユーザーが追加・編集できるので、固定の enum にできない。
`taxonomy.mjs` の中身をそのまま Choice の `criteria` に渡している。
費目を増やしてもパイプラインのコードは変わらない。

### 「分からない」を選択肢として設計する

Choice は候補の外を返せない。だから「該当なし」を返してほしいなら、
**`不明` という選択肢を自分で用意する**。用意しなければ必ず何かを選ぶ。

### 確信度で3段階に分ける

docs 推奨の形。しきい値は「間違えたときの損」で決める。

```
確信度 ≧ 0.85  → そのまま確定
0.50 – 0.85    → ユーザーに確認（2位の候補と並べて二択で聞ける）
確信度 <  0.50  → 採用しない。手入力に回す
```

### 行の仕分けは、除外語リストではなく Choice でやる

最初は「小計・合計・レジ・カード…」という除外語のリストを手で持っていた。
実物のレシートを入れたら、**3つとも違う壊れ方をした。**

```
バイオ50レジ袋特大1枚   5     → `レジ袋` が `レジ` に引っかかって品目から消えた
伝票番号 123-456-789-0123   → 末尾の 0123 が金額として計上された
金額   ¥1,919                → リストに無いので品目として通ってしまった
```

**意味で決めるべきことを文字列一致で書くと、こうなる。**
リストを増やしても、次のレシートで別の形で破れる。

今は、金額のありそうな行を全部 Choice に渡して
「品物 / 小計や合計 / 税 / 支払いや釣り銭 / 番号や識別子 / その他」に仕分けている。
コードが見るのは「そもそも金額の形をしているか」だけ（住所・日付・ハイフン区切りの番号など）。

### 必ず検算する

**行の仕分けを間違えると、合計が必ず合わなくなる。** だから最後に足し算で確かめる。
これは Jev の仕事ではなくコードの仕事。足し算にモデルは要らない。

```
品物の積み上げ  +  消費税  =  レシートの合計
```

外税のレシートでは差がゼロにならないが、消費税は 8% か 10% なので、
差が積み上げの 12% を超えることはまずない。

| 差 | 判定 |
| --- | --- |
| 0 | 一致（税込価格表示） |
| +0 〜 積み上げの12% | OK（税として説明がつく） |
| マイナス | **異常。** 品物でない行を品物として数えている |
| 12% を大きく超える | **異常。** 品物の行を取りこぼしている |

異常なら画面に赤で出して「このまま登録してはいけない」と言う。
黙って間違った家計簿が登録されるのが一番まずい。

実物のレシート（セブンイレブン、軽減税率8%と10%が混在）で検算が通ることを確認済み。

```
品物の積み上げ 1767 = 小計(税抜8%) 1192 + 小計(税抜10%) 575
レシートの合計 1919 = 1767 + 消費税 95 + 消費税 57   → 差 152 = 税額ちょうど
```

**この検算で見つからないものもある。** 数十円の品目を1つ取りこぼしても、
差は税の範囲に収まってしまう。「絶対に正しい」ではなく
「大きく壊れたら必ず気づく」ための仕掛け。

### コードがやることは、コードがやる

全部 Jev に投げない。分担をはっきりさせている。

- **足し算はコード。** 品目の積み上げと Jev が選んだ合計を突き合わせて検算する
- **絞り込みはコード。** 名寄せは履歴 M 件 × 品目 N 件＝ N×M 問になるので、
  文字列の類似度で候補を1件に絞ってから「同じ商品か」だけを Noul に聞く
- **重みはコード。** Score を正規化して金額で重み付けする部分はコードが持つ。
  あとから調整できるし、なぜその数字になったか説明できる
- **選択肢が1つなら呼ばない。** 小分類が1個以下の費目は question を作らない

### 正規表現は「取りこぼすより拾いすぎる」側に振る

店名・合計・日付は、まず正規表現で候補を多めに集める。
どれが正解かは Choice に選ばせる。Choice は候補の外を返せないので、
**「2026」を合計金額としてでっち上げることが起きない。**
値の妥当性チェックを書かなくてよくなる。

### レシート解析について

`candidateLines` は行末の数値だけを金額として取る。
行全体から数字を消すと `食パン 6枚切` が `食パン枚切` になってしまうため。

ここで落とすのは「**そもそも金額の形をしていない**」行だけ
（住所・日付・時刻・`123-456-789-0123` のようなハイフン区切りの番号・マスクされた番号）。
品物かどうかの判断はしない。それは上に書いたとおり Choice の仕事。

## Jev についての注意

- **テキスト専用。** 画像・音声・動画は受け付けない（OCR はできない）
- **生成はしない。** 返ってくるのは選択肢・数値・確率だけ。文章は書けない
- 1リクエストあたり 64k トークン、`state` + 最長の question で 32k まで
- Choice の選択肢は最大 255
- 公式ドキュメント: <https://docs.typesafe.ai>
- `jev-omni` という名前の多モーダルモデルが出回っているが、
  **TypeSafe とは無関係な第三者のモデル**（Gemma のファインチューン）なので混同しないこと

## モックについて

`jev.mjs` のモックは、instructions / state / criteria の**文字の重なり**で
それらしい答えを作っているだけの安物。Jev の挙動の再現ではない。
デモが落ちたときに画面を最後まで見せるためだけのもので、
性能の参考にはまったくならない。
